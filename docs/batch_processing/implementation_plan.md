# バッチ処理機能 実装計画

## 概要

このドキュメントは、matching scoreのバッチ処理機能の実装タスクと優先順位を定義します。

## プロジェクトゴール

**主要目標:**
複数の置換パターン（from_probe、to_probe、match_index）に対して、matching scoreを一括計算できるバッチ処理機能を実装する。

**成功基準:**
1. CSVファイルで複数のジョブを定義できる
2. 全ジョブを自動的に順次または並列処理できる
3. 各ジョブの結果とサマリーが構造化されたCSVで出力される
4. エラーハンドリングが適切で、一部のジョブが失敗しても処理を継続できる
5. 既存の`integrated_substructure_replacement`機能との完全な互換性

## 技術的考慮事項

### 後方互換性

**要件:**
- 既存の`integrated_substructure_replacement`関数は変更しない
- バッチ処理は`integrated_substructure_replacement`をラッパーとして使用

**検証:**
- 既存のテストがすべてパスすることを確認
- 既存のサンプルスクリプトが動作することを確認

---

### パフォーマンス

**目標:**
- 順次処理: 1ジョブあたり平均10-30秒（パターン数による）
- 並列処理: 4ワーカーで3-4倍の高速化

**測定:**
- 各ジョブの実行時間を記録
- バッチ全体の実行時間を記録
- 並列処理のスケーラビリティを測定

---

### エラーハンドリング

**方針:**
- ジョブレベルのエラーは記録して継続（continue_on_error=True時）
- バッチレベルのエラー（CSV読み込み失敗など）は即座に中断
- すべてのエラーにわかりやすいメッセージを提供

**検証:**
- 各種エラーケースのテスト
- エラーメッセージの明確性確認

---

## リスクと対策

### リスク1: 並列処理の複雑性
**影響度:** 中  
**対策:**
- Phase 1で順次処理を完全に実装
- Phase 2で並列処理を追加実装
- 並列処理が失敗しても順次処理で動作する

### リスク2: メモリ使用量
**影響度:** 低  
**対策:**
- 大量のジョブはチャンクに分割して処理
- プロファイルファイルのキャッシング戦略を検討

### リスク3: 既存機能との互換性
**影響度:** 高  
**対策:**
- 既存のテストを全てパスすることを確認
- 既存の関数は一切変更しない
- レビュー時に互換性を重点的にチェック
